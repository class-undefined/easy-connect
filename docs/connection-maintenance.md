# 连接维护与官方行为证据

0.4.9 将连接维护放在隧道传输层。正常连接不请求门户状态接口。传输故障触发会话确认，并尝试恢复已有通道。服务器明确返回注销原因时，客户端结束会话。

## 0.4.14：正式会话续期

正常连接现在同时维护 TLS 数据面和独立 TIMQ/ACKQ 续期。续期复用认证会话，初次 type 4、周期 type 3（约 5 秒）；解析完整 60 字节头并消费有界广播正文。正数有效期更新截止时间，type 2 只确认，不更新期限。I/O 失败关闭连接并用相同 ID 重新握手；恢复同时受剩余有效期与 60 秒无有效响应预算约束。

续期结束会关闭全部数据通道并触发原有会话检查与清理。终止状态不会被较迟完成的门户在线查询覆盖。手动断开中断已登记 socket 和退避等待，线程随数据面 lease 回收；每次认证使用独立状态，旧任务不能覆盖新连接。

会话 ID 替换时整体断开并提示重连，不采用新 ID、不自动登录、不对替换会话发注销请求。透明更新 token、配置、地址及所有通道仍未实现。

此兼容通道**没有加密与服务器身份校验，会明文传送会话 ID**；独立 HTTPS/TLS 的证书校验不能保护它。当前本机网关的 20 秒 P0 测试曾取得 3 次正数有效期。第一次生产测试约 40 秒收到服务器结束；随后发现并停止 `hk` 上仍在运行的同账号 VPN 服务，重新测试通过：空闲连接 900,120 ms、180 次正数续期确认，之后内网 TCP 连接成功，正常退出码 0。此结果限定于本次环境与会话，不单独证明此前断线的唯一原因。本机 GUI 和后台已安装运行 0.4.14；TUN 下 55 条路由、内网 ICMP/TCP 访问和主动断开后的路由/接口清理均已验证。真实物理断网恢复尚未主动制造测试，恢复与取消已由本地模拟服务器覆盖。具体进度见 [会话续期记录](session-renewal-tasks.md)，下方调查表描述实现之前的差距。

## 历史调查：2026-10-13 约五分钟断线

本机 0.4.13 的实际日志显示：隧道已建立、命令心跳已确认，随后控制连接 EOF、接收连接 EOF；门户状态查询失败，使用原会话恢复控制和接收通道时均收到非预期状态，控制通道三次恢复失败后结束连接。这不是命令心跳回复超时日志。用户报告通常约五分钟断开。

**已确认的实现缺口：官方还有独立的登录会话续期通道，0.4.13 Rust 只实现了 L3 隧道心跳。** 两者不能等同。下面的 300 秒是官方客户端的本地初始期限，并非已抓到本次网关下发的超时值；缺失续期与五分钟断线高度吻合，但最终因果仍需真实连接验证。

本轮复用 REA 6.4.0 的 JavaScript 分析，并通过 `inspect-macho` 固定原生文件身份。原生控制流使用 Xcode `llvm-objdump` 对同一文件静态反汇编核对；本机没有可用的 Ghidra、Hopper 或 IDA，不把 Mach-O 元数据描述成反编译结果。

## 官方客户端的行为

### P0 续做：旧式续期的安全边界与网关实验

对同一 CSClient 的 `HandShakeServer` 继续核对：82 字节首包在偏移 44 覆盖 16 字节 TWFID；122 字节回复仅检查读取长度（`0x100051e19`），随后发送固定 43 字节确认。底层实现来自 `libCMS.dylib`，`ConnectSock` 使用普通 TCP（`0xf4ce`、`0xf57d`），`SendData`/`RecvData` 直接调用 `write`/`read`（`0x1000f`、`0xfdcf`）。这条路径没有加密、证书校验或 TLS Finished 验证。libCMS SHA-256：`81b02d152d9cfff9d609a799c0a4a49edaf292e73d3a802b459a35ecf1bf4b6c`。

目标网关已实测接受该报文布局：使用全零占位 ID，完整返回 60 字节 ACKQ type 3（超时/无效会话），广播正文长度 0。这个结果证明协议识别，不能证明有效会话续期、服务器身份或与已登录数据面的共存。

另在独立 `TCPP` TLS 1.1 连接上验证了证书和 Finished；加密发送 TIMQ 后约 3 秒读取超时。官方 `libecbase::_Curl_vpn_connect`（`0x7d2e2`）提供 `C01 HELLO`、`C02 AUTH SESSION`、`C03 CONNECT RESOURCE` 的 TLS 文本资源代理路径；占位 C01/C02 实验分别收到 33/13 字节响应。这些响应及文本路径没有证明续期支持。该库三个读取点都仅检查读取量大于零，不能把任意响应当作认证成功。libecbase SHA-256：`33e8f85069d8c7c5b7e603161fc85531ead7f633cfcde5a7c3981873dd7c6892`。新增库结论来自只读 llvm-objdump，并非新增 REA 反编译结果。

P0 阶段的 `session_renewal.rs` 与两个 `session-renewal-*` examples 最初仅用于诊断；0.4.14 已默认启用正式维护线程，登录示例也复用该生命周期。旧式真实登录诊断仍要求显式接受明文 TWFID 风险。帧读取错误后会关闭诊断 socket，避免半帧重试；广播长度上限 64 KiB 是本地策略。会话切换只分类并停止，未实现 token、资源、地址和数据通道的协调替换。详见 [任务记录](session-renewal-tasks.md)。

用户随后明确授权一次真实会话实验，并在本机终端输入凭据。2026-10-13 10:54～10:55（Asia/Shanghai）的实验中，当前 TLS 数据面建立后 86 ms 收到 ACKQ type 5；第 5,102/10,111/15,122 ms 分别收到 ACKQ type 1，有效期为 2,591,995/2,591,990/2,591,985 秒，广播正文均为 0 字节。20,000 ms 窗口结束时数据传输仍开启，记录 3 次正数有效期，进程退出码 0，注销请求未报错。此结果确认短时协议共存与有效应答；没有安装 TUN 或测试内网访问，也没有完成 15 分钟连接验收。字段值约为 30 天且逐次递减，可能表示剩余总有效期；尚不能推断空闲超时或五分钟断线已修复。

## 本项目的实现

`engine/data_plane.rs` 维护命令、发送和接收通道。命令线程等待 socket 可读事件，空闲约 35 秒时发送协议心跳。发送线程在空闲约 31 秒时发送 ICMP 保活包。真实发送会推迟下一次数据保活。

命令心跳等待回复，并处理分段或合并的命令消息。数据心跳识别与当前会话匹配的 echo reply。只有网关曾成功回复数据心跳，客户端才启用数据回复超时判断。任何合法入站 IPv4 流量都能解除待确认状态。

通道故障触发一次门户查询。查询在线或查询失败时，传输层继续恢复。只有明确会话结束或恢复耗尽，连接才退出。恢复复用现有 token，保留虚拟地址，不重新提交账号密码。

发送或接收故障只重建对应通道。命令恢复先发送命令 1；服务器返回重置时，尝试命令 0。命令通道恢复成功后，客户端关闭旧收发 socket，让收发线程重新建通道。返回的地址必须与当前地址相同，否则退出并清理原网卡、DNS 和路由。

接收通道重建时，丢弃旧连接残留的 IPv4 半包。每次 TLS 重建使用独立加密状态。关闭连接会中断心跳等待、重试退避和已登记 socket 的 TLS 握手。新 socket 会替换登记项，避免只关闭旧连接。

SOCKS 和 TUN 共用上述维护逻辑。退出时关闭传输，再回收后台维护线程。GUI 仍读取本地服务状态；这属于界面状态同步，不会产生门户轮询。

## 兼容性适配与本地策略

本项目使用真实 TLS 封装。官方样本使用旧版 TLS 外观与 IPCP 封装。命令 3、回复 15 和 ICMP 内容来自官方样本；将命令投射到已有 64 字节请求和 36 字节回复结构，属于兼容性适配。

现有 TLS 收发和地址请求格式还参考了 [zju-connect v1.1.1 的协议实现](https://github.com/Mythologyli/zju-connect/blob/v1.1.1/client/easyconnect/protocol.go)。该实现没有补齐本轮的原生命令心跳，不能作为心跳运行验证。

除明确标注来自官方样本的两项外，以下数值是本项目的策略，不能称为官方常量：

| 策略 | 当前值 |
| --- | --- |
| 续期周期 / 本地初始期限 | 约 5 秒 / 300 秒；这两项来自官方样本。 |
| 续期无有效响应预算 | 60 秒，与总有效期分别计算。 |
| 续期单次连接/收发与失败退避 | 3 秒；每次操作共享绝对期限，已登记 socket 可被取消。 |
| 续期广播正文上限 | 64 KiB；完整消费，不记录正文。 |
| 命令心跳回复等待 | 10 秒。已开始的 TLS record 读取还受 socket 超时限制。 |
| 确认支持后的数据回复等待 | 95 秒。后续保活发送不会延长原截止时间。 |
| 每次通道恢复的次数 | 3 次。 |
| 恢复尝试前的等待 | 依次 3 秒、5 秒和 10 秒。 |
| 恢复连接与 TLS socket 超时 | 最多 5 秒；关闭可中断已登记 socket。尚未完成的 TCP connect 受连接超时限制。 |

数据回复超时只重开接收通道。收到新通道流量后继续工作。网关从未回复数据心跳时，接收通道依靠真实 I/O 错误和 TCP keepalive 判定故障；此时尚不能主动识别所有接收黑洞。

## 验证与测试边界

自动化测试覆盖保活包字段与校验和、分段命令应答、回复超时、服务器重置、同会话恢复、地址变化拒绝和 IPv4 半包清理。还覆盖替换 socket 的关闭、取消退避、门户查询失败和健康连接不查询门户。

```sh
cargo test --locked -p ec-compat --lib
cargo test --locked --features desktop --lib
cargo clippy --locked -p ec-compat --lib -- -D warnings
cargo clippy --locked --features desktop --bins -- -D warnings
```

测试使用模拟传输和本地 socket，没有自动登录真实网关，也没有人为踢出真实会话。TLS 命令心跳与恢复请求仍需真实网关验证。测试时先观察空闲连接，再测试网络短暂中断及恢复。日志中的 `VPN command heartbeat confirmed` 和 `VPN data heartbeat confirmed` 分别证明当前网关回复了对应探测。

若出现故障，保留 `VPN Control channel failed`、`recovery attempt` 和 `channel recovered` 日志。它们用于区分协议不兼容、网络故障和恢复失败，不输出 token 或原始报文。
